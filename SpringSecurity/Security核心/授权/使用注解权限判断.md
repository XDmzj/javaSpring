
首先，在你的配置类上开启注解支持：

```java
@Configuration
@EnableWebSecurity
@EnableMethodSecurity // 开启基于方法的安全认证（Spring Security 6.x 推荐）
public class SecurityConfig { ... }
```

开启后，你就可以在 Controller 层的方法上愉快地使用注解了。框架提供了四个主要注解，其中 **`@PreAuthorize` 是绝对的主角**。

#### `@PreAuthorize`（进入方法前校验——最常用）

它在方法执行**之前**进行权限检查。支持 **SpEL（Spring 表达式语言）**，几乎能实现任何复杂的逻辑。


```Java
@RestController
@RequestMapping("/goods")
public class GoodsController {

    // 只要有 'goods:add' 权限就能访问
    @PostMapping("/add")
    @PreAuthorize("hasAuthority('goods:add')")
    public Result add() { return Result.success(); }

    // 必须同时拥有 'ADMIN' 角色 和 'goods:delete' 权限
    @DeleteMapping("/delete")
    @PreAuthorize("hasRole('ADMIN') and hasAuthority('goods:delete')")
    public Result delete() { return Result.success(); }
}
```

#### `@PostAuthorize`（方法执行后校验——针对返回值）

它在方法执行**之后**才进行校验。它允许你通过 `returnObject` 拿到方法的返回值，根据返回值决定要不要抛出异常。

- **场景：** 用户想查看某份订单，只有当“订单所属人 ID == 当前登录用户 ID”时才允许查看。

```Java
@GetMapping("/order/{id}")
@PostAuthorize("returnObject.userId == authentication.principal.id")
public Order getOrder(@PathVariable Long id) {
    // 方法会正常执行并查出数据，但如果上面表达式不成立，Spring Security 会在最后关头把数据“拦截”并报错
    return orderService.getById(id); 
}
```

#### `@Secured` 与 `@RolesAllowed`（老版本遗留）

- `@Secured` 是 Spring Security 早期提供的注解，功能单一，只支持判断角色，且必须带 `ROLE_` 前缀（如 `@Secured("ROLE_ADMIN")`）。
    
- `@RolesAllowed` 是 JSR-250 标准注解，和 `@Secured` 类似。
    
- **结论：** 现代项目**基本不用**这两个了，一律用功能更强大的 `@PreAuthorize`。
