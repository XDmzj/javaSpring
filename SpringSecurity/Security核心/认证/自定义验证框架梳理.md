


第一次接触 Spring Security 时，很多人都会被它内部庞杂的接口、类和过滤器（Filter）搞晕。其实，它的核心设计模式非常简单：**“大经理带着一群专业工人，核对临时通行证的过程”**。

为了让你彻底理清思路，我们从“底层的运行机制”出发，把自定义验证涉及到的每一个核心组件盘一遍。

## 核心组件全景图

在 Spring Security 中，自定义验证主要涉及 6 个核心角色。我们分为 **“数据模型与工具”** 和 **“核心执行引擎”** 两大类来看：

### 1. 数据模型与工具（原材料）

#### 📦 `UserDetails`（接口）

- **它的角色**：**标准的“用户安全档案”**。
    
- **它的功能**：Spring Security 不认识你自定义的 `User` 实体类（比如你数据库里的 `tb_user`）。它只认 `UserDetails`。
    
- **核心方法**：
    
    - `getUsername()` / `getPassword()`：获取账号密码。
        
    - `getAuthorities()`：获取用户拥有的权限/角色集合。
        
    - `isEnabled()` / `isAccountNonLocked()` 等：判断账号是否可用、未锁定。
        
- **需不需要注册为 Bean？**：**绝对不需要！** 它是动态生成的，每个用户登录时去数据库现查现用，是一个“多例（Prototype）”的数据载体，而不是全局单例。
    
- **如何编写**：让你的数据库 User 实体类直接 `implements UserDetails`，或者写一个类去包装你的 User。
    

#### `UserDetailsService`（接口）

- **它的角色**：**“档案管理员（数据源检索器）”**。
    
- **它的功能**：只负责一件事——拿着用户名去数据库（或者 Redis、文件）里把对应的 `UserDetails` 档案捞出来。
    
- **核心方法**：
    
    - `loadUserByUsername(String username)`：**必须重写**。你在这里写 MyBatis 的 `selectOne` 逻辑。
        
- **需不需要注册为 Bean？**：**必须注册为 Bean！**（加上 `@Service` 注解）。因为认证引擎需要自动注入这个管理员来获取数据。
    

#### `PasswordEncoder`（接口）

- **它的角色**：**“验钞机（密码加解密器）”**。
    
- **它的功能**：负责对密码进行不可逆的加密，以及比对前端明文密码与数据库密文是否一致。
    
- **核心方法**：
    
    - `encode(CharSequence rawPassword)`：加密（注册时用）。
        
    - `matches(CharSequence raw, String encoded)`：比对（登录时框架自动调用）。
        
- **需不需要注册为 Bean？**：**必须注册为 Bean！**（通常在 `@Configuration` 配置类里用 `@Bean` 实例化官方推荐的 `BCryptPasswordEncoder`）。
    

### 2. 核心执行引擎（处理机构）

#### 🎟️ `Authentication`（接口）

- **它的角色**：**“临时通行证 / 认证令牌”**。
    
- **它的功能**：在整个登录流程中游走的容器。登录前，它装着前端传来的 `username/password`（未认证状态）；登录成功后，它装着 `UserDetails` 和他的权限列表（已认证状态）。
    
- **核心方法**：
    
    - `getPrincipal()`：登录前是用户名，登录后是 `UserDetails` 实体。
        
    - `getCredentials()`：凭证，通常是密码。
        
    - `isAuthenticated()`：返回 `true` 表示已认证通过。
        
- **需不需要注册为 Bean？**：**不需要。** 纯粹的上下文请求对象，登录时由过滤器动态创建（如 `UsernamePasswordAuthenticationToken`）。
    

####   `AuthenticationProvider`（接口）

- **它的角色**：**“专业的审查工人”**。
    
- **它的功能**：真正干活比对密码的人。它会调用 `UserDetailsService` 捞出档案，再调用 `PasswordEncoder` 去对暗号。
    
- **核心方法**：
    
    - `authenticate(Authentication auth)`：**如果你要魔改逻辑（比如短信验证码验证），必须重写此方法**。如果是普通的账号密码，用系统自带的 `DaoAuthenticationProvider` 即可。
        
    - `supports(Class<?> auth)`：告诉上级，自己能处理什么类型的通行证。
        
- **需不需要注册为 Bean？**：如果你自定义了它，**必须注册为 Bean**。
    

#### `AuthenticationManager`（接口）

- **它的角色**：**“项目经理（认证总负责人）”**。
    
- **它的功能**：统领所有的 `AuthenticationProvider` 工人。它自己不具备任何验证能力，但当过滤器把 `Authentication` 通行证交给他时，他会遍历手下的工人，问：“谁能处理这个？你来办！”
    
- **核心方法**：
    
    - `authenticate(Authentication auth)`：分发认证任务。
        
- **需不需要注册为 Bean？**：在 Spring Security 6.x 中，如果你需要在自己的 Controller 里手动触发登录（比如前后端分离项目中写 `/login` 接口），你**需要在配置类里手动把它暴露出一个 `@Bean`**。
    

## 一张表搞定你的思维导图

|**类 / 接口名称**|**属于框架还是自己写？**|**是否需要注册为 Bean？**|**核心功能职责**|
|---|---|---|---|
|**`UserDetails`**|接口，**自己写**类去实现|❌ 不需要|把你数据库的用户模型，翻译成框架认得的格式|
|**`UserDetailsService`**|接口，**自己写**类去实现|必须（`@Service`）|只负责写根据用户名去数据库查用户的 SQL 业务|
|**`PasswordEncoder`**|接口，直接用**框架自带实现**|必须（`@Bean`）|提供加密算法（如 BCrypt），用于密码比对|
|**`Authentication`**|接口，直接用**框架自带实现**|❌ 不需要|登录请求的上下文包裹器（Token）|
|**`AuthenticationProvider`**|接口，通常用自带的，**魔改时自己写**|如果你自定义了，就必须|真正的“验票员”，执行密码或验证码的比对|
|**`AuthenticationManager`**|接口，直接用**框架自带的经理**|可选（手动登录时通过 `@Bean` 暴露）|认证总入口，负责调用 Provider 工人|
|**`SecurityFilterChain`**|类，直接用自带的，但**要自定义配置**|必须（`@Bean`）|安全大门，配置哪个 URL 放行、哪个 URL 拦截|

## 闭环：它们是如何串联起来的？

当你点击网页上的“登录”按钮，这套底层机器是这样疯狂运转的：

```
[前端请求]
   │
   ▼
1. SecurityFilterChain 拦截到请求，如果是 /login，交给特殊的过滤器。
   │
   ▼
2. 过滤器把账号密码打包成一个未认证的 [Authentication] 令牌。
   │
   ▼
3. 令牌送到经理 [AuthenticationManager] 手里。
   │
   ▼
4. 经理把令牌派发给工人 [DaoAuthenticationProvider]。
   │
   ▼
5. 工人调用你写的 [UserDetailsService]，去 MySQL 查出正确的 [UserDetails] 档案。
   │
   ▼
6. 工人拿着查出来的档案和前端密码，扔给 [PasswordEncoder] 比对。
   │
   ▼
7. 比对成功！工人把档案和权限塞回 [Authentication]，标记为“已认证”，存入全局上下文。登录成功！
```

理解了这套组件的分工，你再去写代码就会发现：**噢，原来我写个 `@Service` 实现 `UserDetailsService`，其实只是给框架的“工人”提供了一个去数据库捞数据的“梯子”而已。**
