## 一、 什么是 CSRF？

简单来说，CSRF 攻击是指：**攻击者盗用了你的身份，以你的名义向某个网站发送了恶意的浏览器请求。**

对于受害网站（比如白马银行）来说，它看到这个请求确实是从你的浏览器发出来的、确实带着你的合法 Session/Cookie，于是网站就会认为这是**你本人的真实意愿**并执行操作。但实际上，你只是在不知情的情况下点击了一个黑客精心伪造的恶意链接。

## 二、 CSRF 的攻击原理（为什么能成功？）

CSRF 能够成功的核心根源，在于浏览器的默认机制：**只要你登录了 A 网站（本地有 Cookie），后续任何时候只要你的浏览器向 A 网站发请求，浏览器都会自动在请求头上带上 A 网站的 Cookie。**

我们可以把整个攻击流程拆解为四个极其精彩的“连环套”：

1. **用户正常登录：** 你访问了正规的**白马银行网站（A 网站）**，输入账号密码成功登录。银行给你的浏览器发了一个 Session ID 并存在 Cookie 里。此时你**没有关闭浏览器标签页**。
    
2. **误入贼船：** 你在同一个浏览器里，不小心打开了另一个充满诱惑或钓鱼的**恶意论坛（B 网站）**。
    
3. **触发机关：** 恶意网站 B 的 HTML 源码里，偷偷埋了一段指向白马银行转账接口的恶意代码。只要你一进网页，这段代码就会自动触发。
    
4. **借刀杀人：** 你的浏览器收到 B 网站的指令，向 A 网站（白马银行）发起了转账请求。由于你之前没登出，**浏览器在发送请求时，会自动把白马银行的合法 Cookie 一并打包带过去！**
    
5. **银行中招：** 白马银行的后端服务器收到请求，一验 Cookie，发现正是你本人的。银行误以为是你自己要转账，当场扣钱，黑客得逞。

## 三、后端程序员如何防范 CSRF？

明白原理后，防范它就很简单了。核心思想是：**不能只信任浏览器自动带过来的 Cookie，必须增加一层“浏览器无法自动伪造”的动态验证。**

### 1. 行业黄金标准：CSRF Token 机制

- **原理：** 当用户正常访问银行首页时，后端随机生成一个由一长串乱码组成的字符串（称为 **Token**），一边存入服务器的 Session，一边传给前端页面（可以藏在 HTML 的 Meta 标签或者表单的隐藏域里）。
    
- **防御：** 当前端通过 Axios 发送转账请求时，**必须在 Headers 里手动带上这个 Token 字符串**。
    
- **为什么能防住：** 黑客在恶意网站 B 里，虽然能通过浏览器“借用”你的 Cookie，但黑客**绝对拿不到**你白马银行页面内部的那个隐藏 Token（因为浏览器有同源策略隔离）。后端一旦发现请求里没有 Token，或者 Token 对不上，直接当成黑客攻击拦截掉！
    

### 2. 现代浏览器大招：SameSite Cookie

现在你不需要写太多代码，只需在后端向浏览器写入 Cookie 时，给 Cookie 加上 **`SameSite=Strict`** 或 **`SameSite=Lax`** 属性。

- 它的意思是：**如果是从别的网站（如黑客网站 B）跨站发过来的请求，浏览器一律不准自动带上我这个网站的 Cookie！** 这从底层直接废掉了 CSRF 的借刀杀人机制。
