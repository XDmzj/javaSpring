
既然要卷校招和底层，那我们就彻底撕掉传统 JSP 时代的“老外衣”，用现代 **前后端分离（RESTful / JSON）** 的视角，重构这张架构图。

## 一、 现代版：前后端分离架构流转图

在现代开发中（比如你的项目中全盘使用的 `@RestController`），右半边的 `ModelAndView` 和 `ViewResolver` 直接被无视了。取而代之的是一条**基于数据流（JSON）的直达通道**。

现代架构的 8 步演进流程如下：

```
[浏览器/前端] 
     │
     │ 1. 发送 HTTP 请求 (携带 JSON 数据, Header: application/json)
     ▼
[DispatcherServlet (中央调度器)]
     │
     ├─ 2. 路由查找 ──> [HandlerMapping (处理器映射器)] (寻找对应的 Controller 方法)
     │ <─ 3. 返回执行链 ─ [HandlerExecutionChain (包含 Controller 和拦截器群)]
     │
     ├─ 4. 权限拦截 ──> [Interceptor.preHandle()] (拦截器前置校验，若返回 false 则直接截断)
     │
     │ 5. 核心适配与分发
     ▼
[HandlerAdapter (处理器适配器)] 
     │
     ├─ 6. 入参解析 ──> 【HttpMessageConverter】(将请求体的 JSON 字符串 反序列化为 Java 对象)
     │                               │
     ▼                               ▼
[Controller (你的业务代码)] <───────┘ (执行业务逻辑，返回普通的 Java 对象/DTO/Result)
     │
     ├─ 7. 出参写回 ──> 【HttpMessageConverter】(将 Java 对象 序列化为 JSON 字符串)
     │
     ▼
[Interceptor.postHandle() / afterCompletion()] (拦截器后置处理与资源释放)
     │
     │ 8. 直接将 JSON 写入 HTTP 响应体 (Response Body)
     ▼
[浏览器/前端] (接收到纯 JSON 数据，由前端 Vue/React 自行渲染页面)
```

### 核心改变在哪里？

- **去视图化**：消灭了 `ModelAndView`。Controller 方法直接返回数据对象（如 `Result<UserVO>`），不再返回逻辑视图名（如 `"index"`）。
    
- **两段式转换**：在进入 Controller 前，JSON 变对象；在离开 Controller 后，对象变 JSON。而这两个方向的转换，全部由同一个幕后功臣完成 —— **`HttpMessageConverter`**。
    

## 二、 深度解密：什么是 `HttpMessageConverter`？

### 1. 宏观定义：它是 Spring MVC 的“高级同声传译员”

`HttpMessageConverter`（HTTP 消息转换器）是 Spring MVC 提供的一个**核心策略接口**。

它的唯一职责就是：**处理 Java 对象与 HTTP 任意报文体（主要是 JSON、XML、纯文本）之间的相互转换。**

- **读（Read）**：把网络上传过来的字节流/字符串（如 JSON），翻译成 Controller 方法里能认的 Java 对象。
    
- **写（Write）**：把 Controller 方法返回的 Java 对象，翻译成网络能传输的字节流/字符串（如 JSON）写回浏览器。
    

### 2. 瞅一眼源码：它长什么样？

作为一个合格的后端，我们直接看它在源码里的核心定义：

Java

```
public interface HttpMessageConverter<T> {

    // 1. 检查：这个转换器能否把当前 HTTP 请求体的数据，读成指定的 Java 类型
    boolean canRead(Class<?> clazz, @Nullable MediaType mediaType);

    // 2. 检查：这个转换器能否把当前特定的 Java 类型，写回为指定的 HTTP 媒体类型（如 application/json）
    boolean canWrite(Class<?> clazz, @Nullable MediaType mediaType);

    // 3. 核心读逻辑：从 HTTP 输入流中读取数据，反序列化为 Java 对象
    T read(Class<? extends T> clazz, HttpInputMessage inputMessage) 
            throws IOException, HttpMessageNotReadableException;

    // 4. 核心写逻辑：把 Java 对象序列化，写入 HTTP 输出流
    void write(T t, @Nullable MediaType contentType, HttpOutputMessage outputMessage) 
            throws IOException, HttpMessageNotWritableException;
}
```

### 3. 常见的全家桶实现（Spring 默认装配了谁？）

Spring MVC 在启动时，会自动在 `HandlerAdapter` 内部注册一个转换器列表（List）。当请求到来时，它会**遍历**这个列表，谁的 `canRead/canWrite` 返回 `true`，就由谁来处理。

|**转换器实现类**|**对应的 MediaType**|**搞定什么数据？**|
|---|---|---|
|**`MappingJackson2HttpMessageConverter`**|`application/json`|**绝对的王者**。底层依赖 **Jackson** 框架，专门负责 Java 对象与 JSON 之间的互转。|
|**`StringHttpMessageConverter`**|`text/plain`、`*/*`|负责处理纯字符串。|
|**`ByteArrayHttpMessageConverter`**|`application/octet-stream`|负责处理字节数组（如下载文件、图片流）。|

## 三、 面试通关：它在底层是如何串联起来的？

大厂面试官最喜欢追问闭环：**“`HandlerAdapter` 是怎么找到并调用 `HttpMessageConverter` 的？”**

这里有三个核心类在打配合，把这个金字塔记在脑子里：

> 1. **`RequestResponseBodyMethodProcessor`（带头大哥）**
>     
>     它既是一个“参数解析器”，又是一个“返回值处理器”。它专门盯防带有 `@RequestBody` 和 `@ResponseBody` 两个注解的方法。
>     
> 2. 当它发现方法上有注解时，它就会说：“这里需要转换数据！” 于是它转头去调用自己内部组合的 `HttpMessageConverter` 列表。
>     
> 3. **`MappingJackson2HttpMessageConverter`（干活小弟）**
>     
>     匹配到 `application/json` 类型，小弟开始干活，调用 `read()` 或 `write()` 方法，内部通过 Jackson 的 `ObjectMapper` 完成最终的 JSON 编解码。
>     

### 💡 为什么懂这个很重要？（实际避坑指南）

你在开发类似`黑马点评`或`苍穹外卖`时，经常会遇到长整型（Long）传到前端丢失精度（后两位变00）的问题，或者 **LocalDateTime 返回给前端格式是一串数组** 的恶心现象。

懂了底层你就知道：这是因为默认的 `MappingJackson2HttpMessageConverter` 在序列化时采用的是 Jackson 的默认配置。

**解决方案**：你只需要在 Spring 容器中自定义配置一个 `ObjectMapper`，给它注册上 `Long -> String` 的序列化器，或者指定 `LocalDateTime` 的格式，然后用它去替换掉 `HttpMessageConverter` 列表里的默认实现。这样，全局的 JSON 返回格式就全在你的掌控之中了。
